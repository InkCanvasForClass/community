# InkCanvas 菜单弹出动画诊断

把菜单弹出/收起动画的**几何行为**放进真实 WPF 管线跑一遍，输出逐帧曲线与几何检查结果。
纯数学部分由 `InkCanvas.NativeInk.Tests` 覆盖；这里只做单测覆盖不到的事——真窗口、真 Popup、真变换。

## 跑法

```bash
dotnet run --project InkCanvas.PopupDiagnostics
# 退出码 0 = 全部通过
```

会短暂弹出一个 900×600 的窗口，检查完自动关闭。

## 检查什么

**曲线形状**（纯数学，秒出）

| 检查 | 说明 |
| --- | --- |
| progress=0/1 精确落位 | 起止点必须严格等于设计值，否则连放会累积误差 |
| 峰值等于 `PopupCurve.PeakScale` | 这个常量同时是宿主留白的依据，对不上就会被窗体裁掉 |
| 全程不超过 PeakScale | 采样 1000 点，任何一个点超了都会在峰值那几帧被切 |
| 透明度权重不被截断 | 权重直接乘进 `Visual.Opacity`，超界会被 WPF 静默夹取 |
| 逐帧表 | 打开/收起的 scale、slide、透明度序列，调手感时看这个 |

**弹窗几何**（需要真窗口，约 1 秒）

| 检查 | 说明 |
| --- | --- |
| 原点落在菜单底边中点 | 菜单弹在按钮上方时，原点纵向必须饱和到 1.0 |
| 原点在首帧后不被重算 | 曾经因为宿主被折叠、窗口按 0×0 重定位，首帧几何是旧值 |
| 过冲全程未被窗体裁切 | 逐帧把内容屏幕矩形和窗口矩形比，21 个采样点全覆盖 |
| 缩放时原点横向不动 | 不动点在缩放方向上必须钉死 |
| 纵向只按设计的滑动量移动 | 纵向位移必须**只**来自 slide，多出来的就是原点没生效 |
| 停稳后底边中点在按钮正上方 | 间距应为 8px |
| 两次打开原点完全一致 | 第一次正常、第二次歪掉是历史上真实出现过的 bug |

## 为什么单独成工程

1. 需要 `UseWPF` 和 STA 线程，不能塞进现有的控制台单测工程；
2. 故意**不加入** `Ink Canvas.sln`，与 `InkCanvas.NativeInk.Tests` 一样不参与 CI——不想给发布流水线增加一个只为诊断存在的产物；
3. 被测代码全部用 `<Compile Include>` 源码链接，避免"测的是拷贝、跑的是原版"。

`MenuHarness` 里复刻了 `AnimationsHelper` 的打开顺序（包装 → 恢复可见 → IsOpen → 解析原点 → 写初值），
每一步都注明对应生产代码的哪一处。改动画流程时这份复刻要一起改，否则测的就不是线上行为了。

## 判定为什么可信

不去比对 `PopupScaleOrigin` 的内部算式（那是自己验自己），而是验它的**外在性质**：
`RenderTransformOrigin` 的定义就是"缩放时保持不动的那个点"，
所以只要缩放前后该点的屏幕坐标不变，原点就确实落在它该在的位置。

注意 `PointToScreen` 的结果会被物理像素对齐量化到整像素，
所以几何类容差取 1px，纯算术比较才用 1e-9——把像素测量的容差设得更小只会得到假失败。
